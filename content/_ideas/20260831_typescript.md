1. TypeScript の型互換性の全部がここから出ます。読後に、「余分なプロパティを持つ変数は代入できるのにオブジェクトリテラルだと怒られる」という excess property check の非対称を予測でき、branded type が必要になる場面を判別できます。空カテゴリの土台として、他の9本すべてが暗黙に前提にする一本です。

2. 面接で最も高い頻度で聞かれる二択で、かつ「好みです」で終わらせない答えが存在します。読後に、declaration merging が要る場面（ライブラリの型拡張）と、union を書きたいので type しかない場面を根拠付きで分けられます。

3. any を禁止するだけの記事は無数にありますが、代わりに何を書くかまで到達しているものは少ない領域です。読後に、unknown を受けて narrowing で開く型と、到達不能を表す never を使い分けられます。catch (e: unknown) もここが引き取ります。

4. 「型が付いているのに undefined が入ってきた」という最も高くつく誤解の解消です。読後に、tsc は境界の外を何も保証しないことを説明でき、fetch の戻りに as User を書くのが検証ではなく黙認であると判別できます。JavaScript 側の提案 #8 error-objects-and-custom-errors と接続します。

5. widening は TS 初学者が最初に踏む「理由の見えない挙動」で、as const と satisfies（TS 4.9+）はどちらもこの一点の対処として登場しました。読後に、as を書きたくなった場面で satisfies に置き換えられるかを判断できます。javascript/var-let-const が持つ「const は immutable ではない」の型側の対応物ですが、const の意味自体は再説明せずリンクします。

6. if の中だけ型が変わるのは TS で唯一「型が動く」場所で、ここを理解しているかで書けるコードが変わります。読後に、x is T の型述語を自分で書け、それがコンパイラへの申告であって検証ではない（＝嘘をつける）ことまで説明できます。instanceof の仕組み自体は JavaScript 提案 #5 に預けます。

7. JavaScript 実行が明示的にこちらへ渡したトピックです（\_ideas/20260831_javascript.md:201「discriminated-unions / 型による表現 — TypeScript。type-system タグの借り手はそちらです」）。読後に、状態を isLoading / error / data の3つの boolean で持つのをやめ、あり得ない組み合わせを型で表現不能にできます。未使用の data-modeling タグの借り手です。

8. 「とりあえず <T> を付ける」と「any に戻す」の間にある判断基準を扱います。読後に、型引数が1箇所にしか現れないなら、それは generic ではなく any の言い換えだという判定ができます。#9 と #10 の両方の前提です。

9. Partial / Pick / Omit / Record をカタログとしてではなく、keyof + mapped type という1つの仕組みの実例として扱います。読後に、ReturnType<typeof fn> のような組み込みを自分で書き下せ、DB の行型から API のレスポンス型を導けます。ReadonlyArray もここです。

10. React カテゴリが存在し、useeffect-cleanup が既にあるのに、型付けの記事がどこにもありません。読後に、React.FC を避ける理由（children の暗黙付与と generic の書けなさ）を説明でき、useState の推論が効かない場面で型引数を足す判断ができます。hook の挙動そのものは React 側の提案が持つので、この記事は型だけを扱います。
