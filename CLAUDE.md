# Kelly's Notes

Content platform for kellybytes.dev — a blog (`/posts`) and a knowledge base (`/kb`) of JavaScript / React / web-fundamentals articles aimed at technical interview prep. Next.js App Router + Contentful, deployed on Vercel.

Articles are authored as Markdown under `content/` and pushed to Contentful by scripts in `scripts/`. Contentful is a delivery target, not the source of truth. See `content/CLAUDE.md` for authoring rules and the article schema.

---

## Hard rules

These override any other instruction in this file. If a task appears to require breaking one, stop and say so instead of finding a way around it.

### Contentful

- **Never call the Management API outside `scripts/`.** Every write goes through `npm run article:push`. Do not write ad-hoc scripts, `node -e` one-liners, or HTTP requests that mutate Contentful.
- **Never publish an `article` entry.** The push script creates and updates article drafts only; publishing is manual, in the Contentful web app. Child entries are the exception — see [Child entries](#child-entries).
- **Never invent or guess a Contentful entry id.** A wrong id links to an unrelated entry and fails silently. A new child entry has no `id` key at all; the script creates it and writes the id back.
- **Gotchas are shared between articles.** Several articles link the same gotcha entry, so writing to one changes every article that references it. Every article that links a gotcha carries its own copy of the fields in frontmatter, and **those copies must be identical**. When an article reuses an existing gotcha, copy the block **verbatim** from the article that already has it — never reword, tighten, or improve it.
- **One id, one symptom.** Never attach an existing gotcha id to a different problem. If the symptom is not the same problem, it is a new gotcha: omit the `id` and give it a new slug.
- **Before reusing a gotcha id, grep `content/knowledge-base/` for it and name the article it came from.** Never write an id you have not seen in another article's frontmatter.
- **Gotcha slugs are unique across the whole space.** Before proposing a new gotcha, grep for the slug. A collision means the gotcha already exists and should be reused, not recreated.
- Never delete, unpublish, or archive an entry.
- Never create or modify a content type, field, or validation.

### Files

- **Never modify an existing article body unless explicitly asked.** Rewriting prose you were not asked about counts as modifying it.
- New articles go to `content/knowledge-base/<category>/<slug>.md` and nowhere else. One file per request.
- `content/_archives/` is read-only. Read it for reference; never edit, move, or delete anything inside it.
- `content/_reference/*.json` is generated by `npm run article:model`. Never hand-edit it. `content/_reference/topic-ownership.md` is hand-maintained and may be edited when asked.
- Never read `.env` or `.env.local`, and never print, summarise, or echo their values.
- `npm run article:pull` overwrites local Markdown. Confirm the working tree is clean before suggesting it, and never run it unprompted.
- Do not create a `CLAUDE.md` anywhere in the tree without being asked.

### Git

- **Never run `git push`.**
- **Never run `git commit --amend`, `git reset`, `git restore`, `git checkout -- <path>`, or `git clean`.** These discard work with no undo.
- Never stage with `git add .` or `git add -A`. Always pass explicit paths.
- If a commit would include changes outside the paths you were asked to commit, stop and list the extra files instead of committing.

### Scope

- **Ask instead of guessing.** Do not apply a "probably correct" change to a file you are unsure about.
- Make the smallest change that does the job. Do not reorganise files, rename things, or clean up adjacent code as part of an unrelated task.
- Do not add dependencies without asking. Script-only deps go in `devDependencies`.

## Stack constraints

- **This project does not use TypeScript.** Do not create `.ts` or `.tsx` files. Do not add type annotations, interfaces, generics, or `as` casts anywhere. If a change seems to require TypeScript, say so and stop — do not migrate files.

## Article pipeline

```
/article-ideas <category>          propose topics — read-only, writes nothing
/new-article <category> <slug>     draft content/knowledge-base/<category>/<slug>.md
                                   new gotchas and questions carry no `id` key;
                                   reused gotchas carry the existing id and an
                                   identical copy of the block

npm run article:push -- <path> --dry-run   validate and report; writes nothing
npm run article:push -- <path>             sync child entries, then create or
                                           update the article draft

   ─── HUMAN GATE ────────────────────────────────────────────────
   Preview the draft in the Contentful web app, then publish it.
   Nothing here publishes an article.
   ───────────────────────────────────────────────────────────────

/commit                            stage content/ and commit
```

A push that creates a child entry writes the new id back into the Markdown, so the file changes on disk. That change is part of the same commit as the article.

`--dry-run` is the review step before a write, not a formality: run it and read the report before pushing an article that already exists.

Markdown under `content/` is the source of truth for everything the pipeline manages.

Two authored content types, two renderers, two pipelines. `article` (KB) has a **Markdown Text** body and is managed by the scripts. `post` (blog) has a **Rich Text** body and a required cover image asset — it is authored in the Contentful web app and the article scripts must not touch it.

## Data fetching (Delivery API)

Every read goes through a `fetchX` function wrapped in `unstable_cache` with a shared `REVALIDATE` from `@/lib/utils`. Follow that pattern exactly when adding one:

```js
const fetchThing = async slug => {
  /* client.getEntries(...) */
};
export const getThing = unstable_cache(fetchThing, ['kb-thing'], {
  revalidate: REVALIDATE,
});
```

- **Use a function declaration or define the wrapper below its dependencies.** `unstable_cache` wrappers assigned to `const` arrow functions throw a TDZ error if referenced above the declaration line.
- Cache keys are flat strings (`'kb-articles-by-category'`). Keep them unique — a duplicate silently serves the wrong data.
- Preview reads must bypass the cache. See `getArticle` in `lib/contentful/kb.js`: the cached path is a separate export and preview calls the raw fetcher.
- Article queries need `include: 2` to resolve `category`, `tag`, `gotchas`, and `interviewQuestions`. Without it those come back as unresolved links. **A gotcha's own `category` and `tag` sit a level deeper than the article's** — confirm they resolve at `include: 2` before rendering them, and raise the level only if they do not.
- **Searching on a referenced entry's fields requires `fields.<ref>.sys.contentType.sys.id`.** It looks redundant when the reference is locked to one content type by validation, but the CDA does not read validations — without it the nested field path cannot be resolved. See `fetchArticlesByCategory` in `lib/contentful/kb.js`. Do not remove it.
- Reference search only works on single-entry links, one level deep. It cannot be used on `tag` (an array of links) — filter those client-side instead.

**The Delivery API omits `fields` for unpublished referenced entries.** A published article linking a draft category, tag, gotcha, or interview question renders an empty section with no error anywhere. Always use optional chaining plus a fallback when reading through a reference, in addition to Contentful's own validation.

## Preview mode

`app/api/preview/route.js` calls `draftMode().enable()` and redirects to the requested path.

- **The preview secret check and `lib/utils/safe-redirect.js` are security fixes. Do not remove or "simplify" either during refactoring.** String-prefix path validation is not safe — backslash handling in the WHATWG URL spec lets open redirects through. Redirect targets must be validated by comparing origins.
- Allowed destinations live in `lib/preview-routes.js`.
- Routes with both `generateStaticParams` and `draftMode()` build as `●` (SSG), not `ƒ`. That is correct: public visitors get static HTML, draft-cookie requests render on demand. Do not "fix" it.

## Markdown rendering (KB bodies)

`components/Markdown.jsx` — `react-markdown` + `remark-gfm` + `rehype-highlight`, no custom `components` override. Styling comes from `@tailwindcss/typography`.

- Allowed: h2–h4, lists, tables, fenced code blocks, inline code, links, blockquotes
- Not available: raw HTML (not enabled), footnotes, math, images
- `h1` is reserved for the `title` field — never use `#` in a body
- **Every fenced code block must declare a language.** `rehype-highlight` leaves untagged blocks unhighlighted.

## Management API (scripts only)

`contentful-management` v12+. The default client is the **plain** client.

- Never use `client.getSpace()`, `space.getEnvironment()`, or `entry.update()`. Those belong to the legacy client and do not exist on the default one.
- Create it with `{ type: 'plain', defaults: { spaceId, environmentId } }`.
- Query params go inside `query`: `client.entry.getMany({ query: { content_type: 'article', limit: 100 } })`. Passing them at the top level is **silently ignored**.
- On update, spread the fetched entry so `sys.version` survives — it is the optimistic lock: `client.entry.update({ entryId }, { ...current, fields })`.
- A page is capped at 100 items regardless of `limit`. Use `getAllEntries()` from `scripts/lib/contentful.mjs` for anything that can exceed 100.
- **Never hardcode a locale.** Call `getDefaultLocale(client)`. A wrong locale key produces empty results with no error.
- The CMA does not expand links. References come back as `{ sys: { id } }` and must be resolved against entries you fetched separately.
- **Omit optional fields that are empty.** `errorMessage:` with no value parses as `null`. Leave the key out of the payload rather than sending `{ [locale]: null }`.

### Entry resolution

- **Articles are resolved by `contentfulEntryId` in the frontmatter, never by slug.** No id means create, and the script writes the new id back into the file. Do not add a slug lookup as a fallback — a near match would overwrite an unrelated article.
- **Child entries are resolved by `sys.id` only.** Never resolve a child entry by slug at push time.
- **Merge, never replace.** On update, send `{ ...current.fields, ...fields }`. Every field the pipeline manages now comes from the frontmatter, but the merge still matters: it is what keeps a field added to the content type later from being wiped before the script knows about it.

### Child entries

Both `interviewQuestion` and `gotcha` are script-owned: the push script creates them when the frontmatter has no `id`, updates them when it does, publishes them, and writes new ids back into the file before touching the article. Children are synced first, because the article needs their ids to build its links.

Publishing children is safe and necessary. A child entry no published article links to is invisible on the site; leaving it as a draft is what breaks, because the Delivery API omits `fields` for unpublished references and the article renders an empty section with no error anywhere.

The two types differ in three ways that matter:

**1. Gotchas are shared. Interview questions are not.**

A gotcha entry is linked by several articles, each carrying its own copy of the block in frontmatter. Writing the entry changes every article that links it.

Before writing a gotcha, collect every article under `content/knowledge-base/` that references the same id and compare their copies of the block. If any copy differs from the one being pushed, **abort without writing** and list the disagreeing files. Shared gotchas must be identical across every article that links them; when they are not, which one is correct is a human decision.

**2. Gotcha slugs are unique across the space.**

Before creating a gotcha, query for an existing entry with the same slug. If one exists, abort and report its id — the gotcha already exists and the article should link it instead of creating a duplicate.

**3. Gotchas have link fields of their own.**

`category` is a required entry link and `tag` is an array of up to three entry links. Resolve both from `content/_reference/categories.json` and `tags.json`, the same way the article does. Note that a gotcha allows **three** tags while an article allows **four** — keep the limits in separate constants.

### Writing ids back rewrites the file

`matter.stringify` re-serialises the whole frontmatter, so any push that creates a child entry can reflow YAML — quoting, line wrapping, and key order are not preserved. Run `git diff` after a push that reports a created entry.

## Known traps in this codebase

- **Module-level client instantiation.** Instantiating third-party SDK clients at module load time breaks Vercel builds — env vars are not injected yet. Instantiate inside the async function that uses it.
- **Effect dependency arrays capture inputs, not outputs.** Including state the effect itself produces causes an infinite loop.
- **React keys control identity.** Same-type siblings in the same tree position keep their state unless the key differs; a differing key forces unmount/remount.
- **Tailwind v4 only emits `@keyframes` when the matching utility class appears in markup.** An inline `style` animation reference without the class has no keyframe to point at.
- **Debug by the shape of the broken output.** What exactly is wrong usually names the culprit — e.g. items grouped correctly but sorted alphabetically points at a local sort function, not the API.

## Conventions

- Conventional Commits: `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `style:`. Single line for straightforward changes. Security fixes and refactors go in separate commits — never mixed.
- Article content commits use `content(kb):`; prose and wording changes use `style(kb):`; formatting-only Markdown changes use `format:`.
